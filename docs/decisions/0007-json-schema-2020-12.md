# ADR 0007 — JSON Schema draft 2020-12, validated with Ajv

**Status**: Accepted
**Date**: 2026-08-05

## Context

The format needs a machine-readable schema so third-party tooling can check documents without
implementing the specification. JSON Schema is the only realistic candidate; the question is
which dialect, and which validator in the reference implementation.

## Decision

Publish the schema in **JSON Schema draft 2020-12**. Validate with **Ajv 8**, confined to
`@openresult/validate`.

## Consequences

- 2020-12 has mature implementations in all seven target languages, so ports validate identically.
- `unevaluatedProperties` lets the schema allow `x-` extensions while rejecting every other
  unknown property — which is what turns a typo into a validation error rather than silently
  discarded data.
- Ajv exposes structured errors, which the diagnostics layer maps to plain-language messages with
  a suggested fix.
- Ajv is a runtime dependency, acceptable only because it never sits on the read or ranking path.
  Were `core` ever to depend on it, [ADR 0006](./0006-dependency-free-core.md) would be broken.

## Alternatives considered

**Draft 07** — broader support in older tooling. Rejected: it lacks `unevaluatedProperties`,
which is precisely the mechanism the extension policy relies on.

**Hand-written validation, no schema** — removes the dependency. Rejected: publishing a schema is
a deliverable in itself, since it is what lets third-party tools consume the format without
reading the specification.
